# [ADR-001] 백엔드·실시간 통신 기술 선택 (Firebase · Supabase · 자체 WebSocket)

- **날짜:** 2026-11-06
- **상태:** 제안

## 배경

나누길 서버가 맡는 일은 크게 두 종류다.

1. **실시간 중계** — 주행 중 차량끼리 위치·속도·상태(휴게소 진입, 정차, 주유 경고)를 주고받는다. 자주 오고, 금방 쓸모가 없어지는 데이터다.
2. **기록과 계산** — 그룹·초대·운행(시작/종료)·차량별 비용·정산 결과를 저장하고, 정산 금액을 계산해 송금 API(카카오페이 등)로 요청을 보낸다. 틀리면 안 되는 데이터다.

결정에 영향을 주는 조건:

| 조건 | 내용 |
| --- | --- |
| 일정 | 공모전 마감 2026-11-15. 남은 기간이 짧아 서버를 직접 만들고 운영할 여유가 거의 없다 |
| 규모 | 그룹당 차량 2~5대, 동시 운행 그룹은 시연 기준 1~2개 |
| 클라이언트 | Kotlin, Android Automotive 기반 Pleos Connect |
| 네트워크 | 차량 통신은 터널·산간에서 끊길 수 있다. 재연결이 자연스러워야 한다 |
| 보안 | 송금 API 키는 앱에 넣을 수 없다. 서버 쪽 코드가 꼭 필요하다 |
| 개인정보 | 위치는 운행 중에만 공유하고, 운행이 끝나면 멈춘다 (README 설계 원칙) |
| 비용 | 학생 팀이라 무료 요금제 안에서 시연까지 가야 한다 |

## 선택지

### 한눈에 비교

| 기준 | Firebase | Supabase | 자체 WebSocket 서버 |
| --- | --- | --- | --- |
| 실시간 위치 중계 | Realtime Database 리스너 (Firestore보다 고빈도 쓰기에 유리) | Realtime **Broadcast** (DB에 안 쓰고 채널로만 전달) + **Presence** (접속 상태) | 직접 구현. 가장 자유롭고 지연도 가장 낮게 만들 수 있음 |
| 그룹·정산 데이터 모델 | NoSQL 문서. 그룹↔멤버↔운행↔비용 관계를 직접 맞춰야 함 | PostgreSQL. 관계·제약조건·트랜잭션을 DB가 보장 | 직접 고른 DB에 직접 구현 |
| 서버 쪽 로직 (정산, 송금 API 호출) | Cloud Functions — **Blaze(종량제) 요금제와 결제수단 등록 필요** | Edge Functions (TypeScript/Deno), 무료 요금제에서 사용 가능 | 서버 코드 안에서 자유롭게 |
| 인증 | Firebase Auth | Supabase Auth | 직접 구현 |
| 접근 제어 | Security Rules | Row Level Security (SQL 정책) | 직접 구현 |
| Android/Kotlin SDK | 공식 SDK, 자료 많음. 일부 기능이 Google Play 서비스에 의존 | `supabase-kt` (Ktor 기반). Play 서비스 의존 없음 | OkHttp/Ktor WebSocket 클라이언트 |
| 오프라인·재연결 | SDK가 오프라인 캐시·재연결 처리 (가장 강함) | 재연결은 SDK가 처리, 오프라인 쓰기 큐는 없음 | 전부 직접 구현 |
| 서버 운영 | 없음 | 없음 | 호스팅·배포·모니터링 직접 |
| 무료 요금제 한계 | Spark 요금제: Functions 불가 | 일정 기간 미사용 시 프로젝트 일시정지, Realtime 메시지·동시접속 한도 | 호스팅 무료 티어 한도 (슬립, 메모리 등) |
| 마감까지 구현 부담 | 중간 | 낮음~중간 | 높음 |
| 종속성 | Google 생태계에 묶임 | 오픈소스, Postgres라 이전 쉬움 | 없음 |

### 선택지별 정리

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. Firebase** | Android 공식 SDK와 자료가 가장 많다. 오프라인 캐시와 재연결이 기본으로 된다. 실시간 리스너가 익숙하고 빠르게 붙는다 | 송금 API를 부르려면 Cloud Functions가 필요하고, 그러려면 종량제 요금제에 카드를 등록해야 한다. 정산처럼 관계가 얽힌 데이터를 NoSQL로 짜면 중복과 정합성 관리가 늘어난다. Pleos Connect에 Google Play 서비스가 없으면 일부 기능(FCM 등)을 못 쓴다 |
| **B. Supabase** | 위치는 Broadcast로 DB를 거치지 않고 흘려보내고, 그룹·정산은 Postgres에 저장해 두 데이터 성격을 한 서비스 안에서 나눠 다룰 수 있다. Edge Functions가 무료 요금제에서도 되므로 송금 API 키를 서버에 둘 수 있다. RLS로 "같은 그룹 멤버만 읽기"를 SQL로 짧게 쓴다. Play 서비스에 의존하지 않는다 | Kotlin SDK 자료가 Firebase보다 적다. 오프라인 쓰기 큐가 없어 끊겼을 때 쌓아 둘 데이터는 앱에서 직접 보관해야 한다. 무료 요금제는 오래 안 쓰면 일시정지되므로 시연 전에 확인해야 한다. Realtime 메시지 수 한도가 있어 위치 전송 주기를 조절해야 한다 |
| **C. 자체 WebSocket 서버** (Ktor/Spring 등) | 프로토콜·주기·데이터 형식을 완전히 통제한다. 특정 업체에 묶이지 않는다. 지연을 가장 낮게 만들 수 있다 | 인증, 그룹 권한, 재연결, 메시지 순서, DB, 배포, 서버 운영을 전부 직접 해야 한다. 마감까지 남은 기간에 정산·합류점 기능과 함께 끝내기 어렵다. 무료 호스팅은 슬립 때문에 첫 연결이 늦을 수 있다 |

## 결정 (제안)

**B. Supabase를 쓴다.** 데이터 성격에 따라 아래처럼 나눈다.

| 데이터 | 처리 방식 | 이유 |
| --- | --- | --- |
| 실시간 위치·속도 | Realtime **Broadcast**, 채널 = `trip:{tripId}` | 매초 쌓이는 위치를 DB에 저장할 이유가 없다. 운행이 끝나면 채널을 닫으면 되니 "운행 중에만 공유" 원칙과도 맞는다 |
| 접속·주행 상태 (온라인/정차/휴게소) | Realtime **Presence** | 누가 채널에 붙어 있는지 서버가 관리해 준다. 끊긴 차량 표시가 쉽다 |
| 그룹·멤버·초대·운행·비용·정산 | **Postgres** 테이블 + RLS | 관계형 데이터라 외래키·트랜잭션으로 정합성을 지킨다 |
| 합류점 알림처럼 꼭 전달돼야 하는 이벤트 | Postgres에 기록 + **Postgres Changes** 구독 | 기록이 남으니 재연결 후에도 놓친 알림을 다시 읽을 수 있다 |
| 정산 계산, 송금 요청 | **Edge Function** | 금액 계산과 API 키를 클라이언트가 아닌 서버에 둔다 |

고른 이유를 줄이면:

1. **마감 안에 끝낼 수 있다.** 서버를 직접 만들지 않고, 인증·DB·실시간·서버 함수를 한 곳에서 쓴다. (C 탈락)
2. **송금 API를 무료로 서버에서 부를 수 있다.** Firebase는 같은 일을 하려면 종량제 요금제가 필요하다. (A의 가장 큰 약점)
3. **정산 데이터가 관계형이다.** 그룹 → 운행 → 차량 → 비용 → 정산 항목이 이어지고, "보낸 돈 = 받은 돈"이 항상 맞아야 한다. Postgres 쪽이 이걸 지키기 쉽다.
4. **Play 서비스 의존이 없다.** Pleos Connect에 Google Play 서비스가 있는지 아직 확인하지 못했는데, Supabase는 그 결과와 상관없이 동작한다.

## 영향

**달라지는 것**
- 이 ADR이 채택되면 README 기술 스택의 "실시간 통신: 미정", "백엔드: 미정"을 각각 "Supabase Realtime (Broadcast·Presence)", "Supabase (Postgres·Auth·Edge Functions)"로 바꾼다.
- 앱 의존성에 `supabase-kt`(Auth, Postgrest, Realtime, Functions 모듈)와 Ktor 클라이언트 엔진이 추가된다.
- 그룹·초대·운행 시작/종료 API는 별도 서버 없이 테이블 + RLS로 만들고, 여러 테이블을 한 번에 바꿔야 하는 곳만 Postgres 함수(RPC)나 Edge Function으로 만든다. 목록은 "그룹·초대·운행 시작/종료 API 목록 초안" 작업에서 정한다.

**감수하는 것**
- 오프라인 쓰기 큐가 없다. 통신이 끊긴 동안의 비용 기록(주유·통행료)은 앱에 임시로 저장했다가 재연결 후 올린다. 위치는 지난 값이 의미 없으므로 다시 보내지 않는다.
- Realtime 메시지 한도를 넘지 않도록 위치 전송은 **2~3초 간격**으로 시작하고, 위치 변화가 작으면 건너뛴다. 받는 쪽은 지도에서 보간해 부드럽게 보이게 한다.
- 무료 프로젝트 일시정지를 피하려고 시연 전 주에 프로젝트 상태를 확인한다.
- Supabase를 못 쓰게 되면 Postgres 스키마와 정산 로직은 그대로 두고 실시간 부분만 자체 WebSocket으로 바꿀 수 있다. Firebase로 통째로 옮기는 것보다 비용이 적다.
