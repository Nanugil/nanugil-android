# [ADR-001] 백엔드·실시간 통신 기술 선택 (Firebase · Supabase · 자체 WebSocket)

- **날짜:** 2026-11-06
- **상태:** 제안
- **작성:** 서버·실시간 통신 담당

## 배경

나누길에는 차량끼리 정보를 주고받고, 그룹과 운행 기록을 저장할 서버가 필요하다. 이 문서는 그 서버를 **어떤 기술로 만들지**만 정한다.

서버가 해야 하는 일은 성격이 다른 두 가지다.

1. **실시간 전달:** 주행 중 위치·속도·상태를 다른 차량에 1~3초 안에 전달한다. 자주 오고 금방 쓸모가 없어진다.
2. **저장과 보호:** 그룹·운행·비용 같은 기록을 저장하고, 같은 그룹 멤버만 볼 수 있게 막는다. 외부 API 키처럼 앱에 넣으면 안 되는 값을 서버에 둔다.

기술을 고를 때 본 조건:

| 조건 | 내용 |
| --- | --- |
| 일정 | 첫 마감 2026-11-15. 서버를 직접 만들고 운영할 여유가 거의 없다 |
| 규모 | 그룹당 차량 2~5대, 시연 기준 동시 운행 1~2그룹 |
| 클라이언트 | Kotlin, Android Automotive 기반 Pleos Connect |
| 네트워크 | 터널·산간에서 끊길 수 있다. 끊겼다 다시 붙는 게 자연스러워야 한다 |
| 보안 | 송금·유가 API 키는 앱에 넣을 수 없다. 서버 쪽 실행 환경이 필요하다 |
| 개인정보 | 위치는 운행 중에만 공유한다 (README 설계 원칙) |
| 비용 | 무료 요금제 안에서 시연까지 간다 |

## 선택지

| 기준 | A. Firebase | B. Supabase | C. 자체 WebSocket 서버 |
| --- | --- | --- | --- |
| 실시간 전달 | Realtime Database 리스너 | Realtime Broadcast (DB를 거치지 않는 채널 전달) + Presence (접속 상태) | 직접 구현 |
| 저장소 | NoSQL 문서 | PostgreSQL (관계형) | 직접 선택·구축 |
| 접근 제어 | Security Rules | Row Level Security (SQL 정책) | 직접 구현 |
| 인증 | Firebase Auth | Supabase Auth | 직접 구현 |
| 서버 쪽 실행 환경 | Cloud Functions. **종량제(Blaze) 요금제와 결제수단 등록 필요** | Edge Functions. 무료 요금제에서 사용 가능 | 서버 코드 안에서 자유롭게 |
| Kotlin 클라이언트 | 공식 SDK, 자료 많음. 일부 기능이 Google Play 서비스에 의존 | `supabase-kt` (Ktor 기반). Play 서비스 의존 없음 | OkHttp/Ktor WebSocket |
| 끊김·재연결 | 오프라인 캐시와 재연결 모두 SDK가 처리 | 재연결은 SDK가 처리, 오프라인 쓰기 큐는 없음 | 직접 구현 |
| 서버 운영 | 필요 없음 | 필요 없음 | 호스팅·배포·모니터링 직접 |
| 마감까지 부담 | 중간 | 낮음~중간 | 높음 |

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. Firebase** | Android 자료가 가장 많다. 끊겼을 때 처리가 가장 강하다 | 외부 API 키를 서버에 두려면 종량제 요금제가 필요하다. Pleos Connect에 Google Play 서비스가 없으면 일부 기능을 못 쓴다. 관계가 얽힌 기록을 NoSQL로 다루면 정합성 관리가 늘어난다 |
| **B. Supabase** | 실시간 전달(Broadcast)과 저장(Postgres)을 한 서비스에서 나눠 쓸 수 있다. 서버 쪽 실행 환경을 무료로 쓸 수 있다. 접근 제어를 SQL로 짧게 쓴다. Play 서비스에 의존하지 않는다 | Kotlin 자료가 Firebase보다 적다. 오프라인 쓰기 큐가 없다. 무료 프로젝트는 오래 안 쓰면 일시정지된다. Realtime 메시지 수 한도가 있다 |
| **C. 자체 WebSocket** | 형식·주기·지연을 완전히 통제한다. 특정 업체에 묶이지 않는다 | 인증, 권한, 재연결, 저장소, 배포를 전부 직접 해야 한다. 마감 안에 다른 기능과 함께 끝내기 어렵다 |

## 결정 (제안)

**B. Supabase를 쓴다.** 데이터 성격에 따라 기능을 나눠 쓴다.

| 데이터 성격 | 쓰는 기능 | 이유 |
| --- | --- | --- |
| 자주 오고 금방 버려지는 값 (위치·속도) | Realtime **Broadcast**, 운행마다 채널 하나 | DB에 쌓지 않는다. 운행이 끝나면 채널을 닫아 "운행 중에만 공유" 원칙을 지킨다 |
| 지금 누가 연결돼 있는지 | Realtime **Presence** | 끊긴 차량을 서버가 알려 준다 |
| 남겨야 하는 기록 | **Postgres** + Row Level Security | 같은 그룹 멤버만 읽고 쓰게 막는다. 테이블 구조는 공통 데이터 모델을 그대로 따른다 |
| 놓치면 안 되는 알림 (예: 합류 지점 안내) | Postgres에 기록 + **Postgres Changes** 구독 | 기록이 남아 재연결 후 다시 받을 수 있다 |
| 비밀 키가 필요한 서버 작업 | **Edge Functions** + 환경변수 | 키가 앱에 들어가지 않는다 |

고른 이유:

1. **마감 안에 끝낼 수 있다.** 인증·저장소·실시간·서버 실행 환경을 한 곳에서 쓰고, 서버를 운영하지 않는다. (C 제외)
2. **비밀 키를 무료로 서버에 둘 수 있다.** Firebase는 같은 일에 종량제 요금제가 필요하다.
3. **기록 데이터가 관계형이다.** 그룹 → 멤버 → 운행 → 비용으로 이어지는 구조라 Postgres가 정합성을 지키기 쉽다.
4. **Google Play 서비스 여부와 상관없이 동작한다.** Pleos Connect의 Play 서비스 지원은 아직 확인하지 못했다.

## 영향

**서버·실시간 통신 담당이 만들어 제공하는 것**
- Supabase 프로젝트, 인증 설정, 접근 제어 정책
- 운행별 Realtime 채널 규칙 (채널 이름, 메시지 형식, 전송 주기)
- 앱에서 쓰는 통신 모듈: 연결·재연결·구독·전송. 다른 담당은 이 모듈을 불러서 쓴다
- Edge Functions 실행 환경과 비밀 키 등록

**다른 담당과 맞출 것**

| 상대 | 맞출 내용 |
| --- | --- |
| PM | 공통 데이터 모델이 정해지면 그대로 테이블과 접근 정책을 만든다. 앱 의존성에 `supabase-kt`와 Ktor 엔진을 추가한다 |
| 차량 데이터·정산 담당 | 정산·송금 로직을 어디서 돌릴지 정한다 (Edge Function이면 실행 환경과 키 등록은 서버 담당이 맡는다). 끊긴 동안의 비용 기록을 앱에 잠시 보관했다가 올리는 방식을 정한다 |
| 지도·그룹 드라이브 담당 | 위치 메시지 형식과 전송 주기를 정한다. 출발점은 2~3초 간격, 움직임이 작으면 건너뛰기 |

**감수하는 것**
- 오프라인 쓰기 큐가 없다. 남겨야 하는 기록은 앱에서 잠시 보관했다가 다시 올려야 한다. 위치는 지난 값이 의미 없으므로 다시 보내지 않는다.
- Realtime 메시지 한도 때문에 위치를 매초 보내지 않는다.
- 무료 프로젝트 일시정지를 막으려고 시연 전에 상태를 확인한다.
- 나중에 실시간 부분만 자체 WebSocket으로 바꿀 수 있다. 저장소와 접근 정책은 그대로 둔다.
